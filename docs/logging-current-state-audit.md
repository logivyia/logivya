# Logging and Observability Current-State Audit

Date: 2026-07-15
Scope: backend APIs, worker and queues, web, mobile, audit records, security events, retention, and privacy controls.

This report records the state found before the centralized logging implementation. It is an engineering audit, not a legal-compliance statement and not proof of production deployment.

## Executive Summary

LOGIVYA already has useful observability foundations. The existing custom structured logger is used broadly, campaign and queue correlation IDs exist in critical delivery paths, domain audit tables exist, mobile Sentry is configurable, and the administrator has real audit and security views. These mechanisms should be consolidated and hardened, not replaced by a competing logger.

The main risks are an incomplete logging contract, fragmented request ID generation, weak recursive redaction, unsafe identifiers in some worker logs, uncontrolled console calls, missing release metadata, convention-only audit immutability, raw IP and email handling without a documented retention basis, incomplete client error scrubbing, and no enforceable retention or alert lifecycle.

## Static Findings

- 393 shared-logger references were found in production source paths.
- 17 direct `console.*` calls were found in production source paths.
- No Pino, Winston, or OpenTelemetry logger dependency is installed. Adding one is not currently justified.
- Mobile uses `@sentry/react-native`; no approved web error provider integration was found.
- Request IDs are generated by multiple helpers and are not attached consistently to every request or response.
- The current logger supports only `info`, `warn`, and `error`; it lacks `debug`, `fatal`, child context, service/release defaults, safe error classification, and test capture.
- The current redaction expression does not cover QR data, pairing codes, TOTP and recovery data, card data, message content, JIDs, or case-insensitive variants comprehensively.
- `AuditLog` lacks actor type, result, reason, request/correlation IDs, platform/version context, safe before/after fields, and retention metadata.
- `SecurityEvent` lacks workflow status, correlation/request IDs, event code taxonomy enforcement, acknowledgment, investigation notes, and retention metadata.

## Privacy and Secret Risks

1. Worker send-attempt logs contain raw external contact and group identifiers (`contactJid` and `groupExternalId`). Internal database IDs are sufficient.
2. Mobile crash reporting can attach the user's full email to Sentry.
3. Mobile and server error contexts are not passed through one shared safe-metadata policy.
4. The web route error boundary renders `error.message` directly to the user.
5. Audit and security records currently store raw forwarded IP values. Continued full-IP storage requires a documented legal basis and access/retention decision.
6. Admin audit views can display full actor email values instead of a masked representation.
7. Local build/runtime logs have no enforceable retention and must be treated as developer-local artifacts.

No evidence was found that message bodies, QR values, pairing codes, access tokens, refresh tokens, passwords, or WhatsApp credential snapshots are intentionally required in operational logs. Tests must make their appearance a release-blocking failure.

## Correlation and Release Findings

- Campaign, recipient, recurring, delete, support, subscription, and selected mobile WhatsApp paths already propagate correlation IDs.
- Generic backend requests do not yet receive a consistently validated request ID and response header.
- Client-supplied identifiers are only truncated in several helpers; a controlled character/length policy is missing.
- Queue events generally carry campaign correlation IDs but do not consistently include request ID, duration, attempt, max attempts, or final-attempt state.
- Environment, service name, Git commit, deployment ID, release version, and app version are not injected centrally into every structured log event.

## Audit and Security Findings

- Central and domain-specific audit tables are complementary, but central taxonomy is free-form and inconsistent (`dot.case`, uppercase, and domain variants coexist).
- There is no application API that intentionally edits or deletes `AuditLog`, but immutability is convention-only and not documented as a database policy.
- Administrator authorization failures create security events, but request IDs and masked network metadata are incomplete.
- Several high-risk admin mutations write central audit records after the mutation rather than in the same transaction. Mandatory audit failure behavior is therefore inconsistent.
- Login/MFA security events exist, but generic failed-login and unknown-account paths need one privacy-safe taxonomy.
- Tenant-denial events are not uniformly emitted by ownership guards.

## UI and Access Findings

- Platform audit and security pages are backend-guarded by the platform-admin guard.
- Normal users have a company-scoped activity endpoint; platform-wide audit APIs are admin-only.
- Web Audit Center is a fixed recent list rather than a complete paginated/filterable center.
- Security Event Center is read-only and lacks acknowledgment and investigation-note workflows.
- Mobile admin definitions already include audit and security modules, so parity should extend the existing generic module screen rather than create a new navigation system.
- Cache isolation and logout invalidation must be covered by tests before release.

## Retention, Storage, Metrics, and Alerts

- No approved category-specific retention values are enforced in code.
- No automated deletion/anonymization job was found for operational, security, or audit data.
- Long-term audit, full IP, support content, payment events, and device-signal retention remain legal/business decisions.
- Existing metric tables can support aggregates, but no centralized low-cardinality observability metric contract exists.
- No durable, deduplicated operational alert model or acknowledgment flow was found.
- External log export is not configured in this repository and will remain disabled unless processor, region, access, cost, and retention review are approved.

## Stable-Core Impact Assessment

The WhatsApp/session/message code is protected. Required changes inside worker and delivery files are limited to removing unsafe log fields, propagating context already present, and normalizing event emission. No pairing, reconnect, session persistence, queue retry, delivery, subscription gate, ownership, or Delete for Everyone business rule may change as part of this phase.

Any change in protected files requires the stable-core regression suite. Logging failure must remain non-blocking for message delivery and WhatsApp recovery.

## Implementation Decision

1. Harden the existing logger and redaction modules instead of adding a second logging library.
2. Add one shared event contract, taxonomy constants, release metadata, safe error serialization, request/correlation validation, and test capture.
3. Extend existing Prisma audit/security models backward-compatibly and add a durable alert model only where the admin workflow requires it.
4. Normalize existing audit/security writers and admin APIs; preserve domain audit tables.
5. Remove direct console use from production paths through a repository check that excludes approved CLI/build tooling.
6. Configure mobile Sentry privacy without enabling a new external provider.
7. Add internal web/mobile client-event boundaries with strict allowlists and sampling; never accept arbitrary client payloads.
8. Implement retention as explicit policy plus dry-run-safe cleanup. Legal-review values remain configurable and documented.
9. Add secret-leak, tenant, correlation, immutability, performance, and stable-core tests before any deployment decision.

## Open External Decisions

- Legal basis and exact retention for full IP addresses.
- Security and administrator audit retention periods.
- Sentry processor region, contractual terms, and production retention.
- External log storage/export provider.
- Alert delivery destinations and on-call ownership.
- Whether immutable audit identifiers are anonymized or retained during data-subject deletion.

These decisions cannot be proven by repository code and must not be represented as completed legal compliance.
